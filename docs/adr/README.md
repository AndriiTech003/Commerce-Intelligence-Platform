# Architecture Decision Records

Формат — [MADR](https://adr.github.io/madr/), один файл на решение: `NNNN-short-title.md`. Ниже список решений с сутью. При реализации каждый пункт разворачивается в отдельный файл по шаблону внизу.

| # | Решение | Альтернативы | Почему / компромисс |
|---|---|---|---|
| 0001 | **Модульный монолит** для domain-логики + отдельные сервисы для ingestion, воркеров и WS | Микросервисы на каждый bounded context | Checkout требует одной транзакции по 4 модулям. Выделено только то, у чего другой профиль нагрузки. Минус: общий деплой API |
| 0002 | **Shared schema + tenant_id + PostgreSQL RLS** | Schema-per-tenant, DB-per-tenant | Просто мигрировать, дёшево, защита на уровне БД. Минус: noisy neighbours, накладные расходы RLS (замерить) |
| 0003 | **Drizzle ORM** | Prisma, TypeORM, Kysely | SQL-подобный, контроль транзакций и `SET LOCAL`, без отдельного движка. Минус: меньше «магии» для связей |
| 0004 | **Transactional outbox + relay с SKIP LOCKED и LISTEN/NOTIFY** | Публикация после commit, CDC (Debezium) | Гарантия доставки без распределённых транзакций, без тяжёлой инфраструктуры. Минус: relay — потенциальное узкое место |
| 0005 | **At-least-once + идемпотентные consumers** (Redis-дедуп для трекинга, `processed_messages` в транзакции для доменных) | Exactly-once брокер | Честная модель доставки. Разные уровни гарантий для разной ценности данных |
| 0006 | **Retry через TTL-очереди + DLX** | Плагин delayed-message, ретраи в памяти | Работает с quorum-очередями, переживает рестарт consumer'а. Минус: фиксированные ступени задержки |
| 0007 | **RabbitMQ**, а не Kafka | Kafka/Redpanda, Redis Streams | Маршрутизация, per-message ack, DLQ, умеренный объём. Минус: нет replay всей истории, поэтому история хранится в ClickHouse |
| 0008 | **ClickHouse** для аналитики | Postgres + партиции, TimescaleDB | Колоночное хранение, MV, `windowFunnel`, сжатие. Минус: ещё одна БД в эксплуатации, eventual dedup |
| 0009 | **Двухуровневый дедуп событий** (Redis NX + ReplacingMergeTree) | Только ReplacingMergeTree, только Redis | Redis отсекает почти всё сразу, ReplacingMergeTree страхует при потере Redis |
| 0010 | **Ручные батчи в stream-worker**, ack после insert | ClickHouse `async_insert` | Контроль над ack и ретраями. Минус: код батчинга свой |
| 0011 | **pgvector в основной БД** | Qdrant, Pinecone | < 1M векторов, фильтр по тенанту и наличию в одном SQL. Минус: HNSW + фильтр = риск недобора (post-filter), решается `ef_search` и итеративным сканированием |
| 0012 | **Профиль с экспоненциальным затуханием, коммутативные обновления** | Пересчёт из истории, партиционирование по пользователю | Порядок событий не важен, consumers масштабируются свободно |
| 0013 | **LLM вне hot path** (офлайн-генерация + human approval) | Генерация на лету под пользователя | Латентность, стоимость, безопасность бренда, воспроизводимость |
| 0014 | **Thompson sampling по сегментам** | A/B с фиксированным сплитом, ε-greedy, UCB, контекстный bandit | Меньше потерь во время обучения, естественная разведка, простая реализация. Минус: сложнее классическая стат. значимость, поэтому есть holdout |
| 0015 | **Основной сегмент по приоритету** для разбиения bandit'а | Bandit на каждое пересечение сегментов | Непересекающиеся контексты, достаточно данных на каждый arm |
| 0016 | **Объяснения шаблонами из реальных признаков**, не LLM | LLM-объяснения | Никаких выдуманных причин, детерминированность, тестируемость |
| 0017 | **Персональные блоки отдельно от кэшируемой страницы** (Suspense / no-store) | Полный SSR без кэша, edge personalization | Кэш не протекает между пользователями, витрина остаётся быстрой |
| 0018 | **`ws` + Redis pub/sub** для realtime-gateway | Socket.IO, SSE | Контроль протокола. Данные однонаправленные, поэтому SSE тоже подошёл бы, но WS оставлен под будущие команды из админки (компромисс описать честно) |
| 0019 | **zod-схемы как единый источник контрактов** (API, события, формы) → OpenAPI → клиент | class-validator + Swagger-декораторы | Один источник правды для фронта, бэка и событий |
| 0020 | **Idempotency: Redis-ключ + уникальный индекс в БД** | Только БД, только Redis | Быстрый путь и надёжная страховка |

## Шаблон

```markdown
# NNNN. Title

- Status: accepted | superseded by NNNN
- Date: YYYY-MM-DD

## Context
Какая проблема, какие ограничения (нагрузка, команда, бюджет, сроки).

## Decision
Что выбрали, одним-двумя абзацами.

## Alternatives considered
- Вариант A — плюсы / минусы
- Вариант B — плюсы / минусы

## Consequences
- Положительные
- Отрицательные и как с ними живём
- Что заставит пересмотреть решение (триггеры: «если > N тенантов…»)

## Verification
Какой тест или метрика подтверждает, что решение работает.
```

Пункт **Verification** есть не во всех ADR, но именно он отличает этот проект: у каждого решения есть тест или цифра.
