# 0003. Drizzle ORM with SQL-first migrations

- Status: accepted
- Date: 2026-10-02

## Context

The data layer has requirements that many ORMs handle poorly:

- explicit transactions with `set_config('app.tenant_id', …, true)` as the first statement (see ADR 0002);
- conditional updates such as `reserved = reserved + q where on_hand - reserved >= q` (ADR 0021);
- PostgreSQL-specific types and operators: `ltree` (`<@`, `subpath`, `nlevel`), generated `tsvector`
  columns, `pg_trgm` similarity, `citext`, `inet`, and later `pgvector`;
- RLS policies, roles and triggers that no schema DSL expresses.

We also want typed results end to end without a separate query engine process.

## Decision

Use Drizzle ORM with node-postgres.

- Schema: `apps/api/src/db/schema.ts`. PostgreSQL types without first-class support (`citext`, `ltree`,
  `tsvector`, `inet`) are declared with `customType`; the `search_tsv` column is `generatedAlwaysAs(...)`.
  The schema also exports `TENANT_TABLES`, used by migrations review and the isolation test.
- Migrations: `apps/api/src/db/migrations/`:
  - `0000_extensions.sql` — custom: `citext`, `ltree`, `pg_trgm`, `vector`;
  - `0001_init.sql` — generated by `drizzle-kit generate` from the schema;
  - `0002_rls_roles_outbox.sql` — custom: roles, grants, RLS policies, the `outbox_notify` trigger, extra trigram/price indexes.
- Migration runner: `runMigrations()` in `apps/api/src/db/migrate.ts` uses the Drizzle migrator and wraps it in
  `pg_advisory_lock(hashtext('cip_migrations'))`, so parallel starts (tests, smoke, several API instances) do not race.
- Queries: Drizzle's query builder for ordinary CRUD; the `sql` template for ltree subtree queries and
  moves, full-text plus trigram search and ranking (`catalog/infrastructure/catalog.repository.ts`), and
  stock reservation updates (`inventory/infrastructure/inventory.repository.ts`). The template is parameterised, so this stays injection-safe.

## Alternatives considered

- **Prisma** — great DX and relations, but a separate query engine, interactive transactions with
  limitations, weak support for `SET LOCAL` per transaction with pooled connections, and raw SQL loses types.
- **TypeORM** — decorators and active record fit Nest, but its type safety is weak and its migration
  generator is unreliable with custom types.
- **Kysely** — excellent typed SQL builder, close to Drizzle in spirit; it has no schema-to-migration
  generator, so we would hand-write all DDL.
- **Raw `pg` only** — full control, but no type inference on results and much more boilerplate.

## Consequences

- Positive: the SQL that runs is the SQL we wrote; transaction handling with `SET LOCAL` is trivial.
- Positive: typed rows for the builder path; schema and generated migration stay in sync via `drizzle-kit check`.
- Negative: no relations magic. Aggregates are loaded with explicit joins or several queries, and
  repositories map rows to domain objects by hand.
- Negative: raw `sql` fragments return loosely typed rows; repositories declare the row type explicitly and
  integration tests cover those queries.
- Negative: RLS and roles live in a hand-written migration that Drizzle does not know about. A new tenant
  table needs a manual policy; the isolation test fails if one is missing.
- Revisit when: Drizzle cannot express a needed feature without raw SQL in most queries, or the project
  needs a DB other than PostgreSQL.

## Verification

- Every integration suite creates a fresh database and runs `runMigrations()` on it
  (`apps/api/test/integration/support/resources.ts`), so the migrations are checked from an empty DB on every run.
- `tenant-isolation.test.ts` fails if a table in `TENANT_TABLES` lacks forced RLS and a policy.
- `catalog.test.ts` covers the raw-SQL paths: ltree subtree moves, full-text plus trigram search, cursor pagination.
