## Deviations from the spec and decisions taken

Part 1 (still valid): no CI/git of any kind; Docker not installed so `docker-compose.yml`/Dockerfiles and
Testcontainers mode are written but not run (compose now also has the embeddings server and Jaeger instead of Tempo);
NestJS without decorator metadata (`@Inject` everywhere); RLS policy detail for memberships; publishable key kept in
tenant settings; outbox relay partial-failure handling; Redis counters claim-before-apply; manual spans for HTTP and
AMQP (pg and ioredis are auto-instrumented since 2026-10-05); storefront tenant routing through middleware + rewrite;
fake payment webhook delivered by a persisted dispatcher (was an in-process timer until 2026-10-05); admin UX scope
choices from part 1.

Part 2:

1. **Embeddings: 384 dimensions.** Migration `0003` changes `products.embedding` from `vector(1024)` to `vector(384)`
   and adds `embedding_source_hash`. Providers (`EMBEDDINGS_PROVIDER`): `hash` (deterministic feature hashing, the
   default in code, used by tests, smoke and e2e), `local` (the new `apps/embeddings-server`, all-MiniLM-L6-v2
   quantized ONNX on CPU over an OpenAI-compatible HTTP API — the dev/demo choice), `openai` (`dimensions: 384`),
   `voyage` (requests 512 dims and truncates to 384 + renormalizes, relying on Matryoshka training — not verified
   because no keys and no external calls are allowed). The server listens on **4189**, not 4190: 4190 is on the WHATWG
   "bad ports" list and Node's `fetch` refuses it. Embeddings are recomputed only when `embedding_version` or the text
   hash changes. The seed embeds the demo catalog with the configured provider.
2. **LLM.** `LLM_PROVIDER=fake|anthropic|openai`, default `fake`. The Anthropic adapter uses the official SDK with
   `output_config.format` (JSON schema) and `effort: low` (default model `claude-opus-5-5`); the OpenAI-compatible
   adapter uses `response_format: json_schema` over fetch. Both are tested with mocked HTTP only; per the local-only
   rule no real provider is ever called. `FakeLlmClient` is deterministic, follows instructions it finds in the
   untrusted product block (to prove guardrails catch it) and sometimes adds an unverifiable "Now 25% off".
3. **Generation API.** One LLM call per selected segment returns `count` variants spread across the selected tones;
   `async: true` returns a job immediately (admin polls `GET /v1/admin/jobs/:id`), otherwise drafts are returned
   synchronously. The daily limit returns `429 LLM_LIMIT_EXCEEDED`; cache hits by `inputHash` are free and do not use
   the quota.
4. **Guardrail actions.** `too_long` and `profanity` reject (the variant is not stored; reasons go to the job errors);
   `unverified_claim` and `prompt_injection` block approval until the draft is edited (guardrails re-run on edit);
   `banned_claim`, `near_duplicate`, `language_mismatch` are flags shown to the reviewer. Profanity uses a word list
   (no moderation API). Language detection is a stopword heuristic.
5. **Review semantics.** Approving a draft of a live campaign makes it `active` at once; otherwise it becomes `approved`
   and is activated with the campaign. The review queue requires `marketing:approve`.
6. **Bandit storage.** Hash `bandit:{campaign}:{segment}` with `{creative}:a`, `:b` (floats, so γ works) and raw
   `:n`, `:s` counters. γ is applied to all arms of the context on every new impression. The success script also counts
   the impression if the click arrives first. No TTL on bandit hashes (as specified).
7. **Holdout** (10% by hash of profile + campaign): uniform creative + popular products, policy `holdout_uniform`; its
   feedback is not fed to the bandit; holdout vs personalized CTR is computed from ClickHouse (`events` ⨝ `decisions`).
8. **Conversions.** The API publishes a server-only `ad_converted` track event (the collector rejects it from clients)
   so `campaign_stats_hourly` and the experiment screen see conversions. Attribution is set at checkout from the last
   click stored in Redis for 24 h and filled in later by the feedback consumer if the click event arrived after
   checkout.
9. **Jobs placement.** Profile snapshots (every `PROFILE_SNAPSHOT_INTERVAL_MS`, default 10 min), VIP threshold (daily,
   p90 of snapshot LTVs, needs ≥ 10 buyers) and bandit snapshots (5 min) run in the API behind Redis locks; popular
   lists (10 min) and price quantiles (1 h) run in the stream worker.
10. **Profile model details.** Affinities are commutative; the price EWMA (α = 0.2) and the 30-minute intent window are
    order/processing-time dependent; a merge keeps the customer's EWMA if it has one. Price band uses quantiles of
    viewed prices of the profile's top-level category from ClickHouse, falling back to catalog prices before any data
    exists. `lapsed` uses a derived feature `days_since_last_order` because the operator list has no negation.
11. **Demo segments for the simulator.** The seed adds `premium_shoppers` (price EWMA ≥ $250), `runners`
    (`aff.cat.running ≥ 3`) and `hikers`; the seeded campaign targets them plus `price_sensitive`. The persona file uses
    base CTR 0.08 (0.03 for window shoppers) so a 10-minute run on one laptop collects enough clicks.
12. **Simulator behaviour.** Sessions use the real storefront API, collector and fake payment; a home decision is
    requested at landing and again when the visitor returns to the home page after browsing. "Segment it mostly lands
    in" counts only warm decisions (returning visitor or after browsing), because every brand-new visitor starts in
    `_default`. Regret is expected regret against an oracle that knows each persona's CTRs; the uniform shadow policy is
    evaluated on the same decisions. Backfill publishes history straight to RabbitMQ (track exchange, including order
    events) so it reaches only analytics: no orders in Postgres, no bandit/notification/webhook side effects.
13. **Duplicate gap from part 1 fixed.** Before inserting, the analytics sink asks ClickHouse which event ids of the
    batch already exist (same tenant/date range) and drops them, so duplicates that slip past Redis no longer reach the
    per-minute and product MVs; covered by an integration test that deletes the Redis dedupe keys and redelivers.
14. **Feature flags (project 02).** `@ashamrai/flags-node` and `@ashamrai/flags-evaluator` are vendored as tarballs
    produced by `pnpm pack` in project 02 (`vendor/`, wired with `pnpm.overrides`). Without `FLAGS_RELAY_URL` +
    `FLAGS_SDK_KEY` the SDK runs offline from a bootstrap ruleset whose fallthrough is `AI_CREATIVES_DEFAULT` (default
    on); per-tenant targeting is covered by unit tests. The project 02 relay was not started.
15. **Observability tooling.** Prometheus and Grafana from Homebrew with project-local configs (ports 4191/4192);
    Jaeger 2.20.0 instead of Tempo (Tempo is not in Homebrew; 2.21 broke Grafana's Jaeger datasource). The Jaeger
    binary (checksum-verified) and Grafana 13's Prometheus/Jaeger datasource plugins were downloaded once from their
    official sources by `scripts/observability.sh` before the stricter local-only rule; they are cached under
    `.observability/` and nothing is downloaded again (`preinstall_disabled = true`, Grafana phone-home disabled). Loki
    was not set up. The RabbitMQ Prometheus plugin is not enabled on the shared broker, so queue metrics come from
    `infra/prometheus/rabbitmq-exporter.mjs` (management API). Ports 4193–4198 are used by Jaeger and the exporter.
16. **Terraform** is validated with OpenTofu because installing `terraform` needs a Homebrew tap (a git clone).
17. **Chaos adaptations.** Docker commands became `kill -9` + restart of the service process (`scripts/stack-ctl.mjs`),
    `brew services stop/start rabbitmq`, `SIGSTOP`/`SIGCONT` of the shared ClickHouse server (pauses it for every local
    project for 120 s), deletion of the stack's Redis prefix instead of `FLUSHALL` (other projects share Redis).
18. **Webhook secrets** are stored in plaintext (needed to sign); only the prefix is shown after creation. Retry
    schedule is configurable (`WEBHOOK_RETRY_SCHEDULE`, tests use 1 s).
19. **CSV import** creates products (rows grouped by `handle`); it does not update existing ones; duplicate SKUs are
    reported per row.
20. **Stack tooling.** `scripts/stack.mjs` gained `STACK_SERVICES` (start a subset) and `STACK_CHAOS` (tolerate killed
    children), and now also starts the simulator; smoke ports are 4180–4187. Its Redis teardown now handles very large

21. **docs/10** is not edited (conventions forbid rewriting the spec); its "known limitations" section is filled in

22. **Metrics added for dashboards:** `orders_placed_total`, `orders_paid_total`, `order_revenue_cents_total`,

## Post-review fixes (independent verification, 2026-10-03)

- **Duplicate merchant webhook delivery (real bug).** `WebhookDispatcher.enqueue` inserted deliveries with `next_attempt_at = now()` and delivered them inline, while the periodic `deliverDue` poller could select the same row and send it again. Inline deliveries now start with a 2-minute lease (`next_attempt_at = now() + interval '2 minutes'`), the same lease `deliverDue` takes, so the poller only picks a delivery up if the inline attempt never finished. Regression test: `apps/domain-worker/test/integration/webhook-dispatch.test.ts` (fails on the old code, passes on the new one; also covers recovery of a delivery left pending by a crashed inline attempt).
- **Flaky ClickHouse dedupe test.** The "duplicates that slip past Redis" test read the tenant-wide `events_per_minute` total, which also counted late-flushing events from earlier tests in the same file. The test now writes its events into a dedicated past minute bucket and checks only that bucket; the dedupe logic itself was correct.

## Gap closure (2026-10-05)

Wave-2 follow-up from `devinfra/PROGRESS.md` ("01 gaps"). Everything below was measured or tested on the same M1
laptop (8 cores, 8 GB) with devinfra running; other agents' workloads were running at times, so every timing records the
load average it was taken under.

### 1. RLS overhead, measured properly (`scripts/rls-bench.mjs`, `pnpm bench:rls`)

Method: the script provisions a throwaway stack database (`cip_test_smoke_rlsbench*`), seeds it, clones the RunHub
catalog into 38 more tenants (40 tenants, 11,850 products, 43,592 variants, 80,000 orders, 160,000 order items) and
creates a byte-identical copy with `CREATE DATABASE … TEMPLATE`, in which RLS is disabled on every table. Then:

- **SQL level**: ten queries copied from the repositories (category/product by slug, variants + stock, storefront list,
  category page, full-text search, trigram suggest, admin orders list, order detail, stock reservation `UPDATE`
  rolled back). Variant **RLS** = role `app_user`, FORCE RLS, `BEGIN; set_config('app.tenant_id'); query as the app
  writes it (no tenant predicate); COMMIT`. Variant **no RLS** = same role on the copy, the same query plus the
  explicit `tenant_id = $n` a non-RLS app would need. A third variant adds the explicit predicate under RLS too.
  2,000 iterations per query after 200 warm-up; every iteration runs all variants in random order on dedicated
  connections (interleaved, so machine noise hits both sides), the same random parameters for each variant; results
  must return the same rows (checked: all equal).
- **HTTP level**: two production API processes (ports 4178/4179) on single-tenant copies of the seeded database
  (RLS vs RLS disabled) — single-tenant because the repositories rely on RLS, so a non-RLS database with several
  tenants would leak rows and make the comparison meaningless. Eight endpoints (catalog list, category page, PDP,
  suggest, add to cart, admin orders list/detail, admin products), 600 requests per endpoint and variant after 60
  warm-up, interleaved in random order.
- **Statistics**: median and p95 per side; overhead = p50(RLS)/p50(no RLS) − 1 with a 95% bootstrap confidence
  interval (2,000 resamples of iterations); the run is also split into four blocks to show stability.

Findings and fixes (three full runs, all kept in `docs/assets`):

1. `rls-bench-before.md` (original policies, load 3.4): list endpoints were **26–43% slower with RLS**
   (catalog list p50 7.19 → 10.26 ms, admin orders 7.03 → 8.83 ms). The plans show why: the policy
   `tenant_id = current_setting('app.tenant_id')::uuid` is evaluated per row in every correlated subquery
   (variants, images, inventory). **Fix — migration `0005_rls_initplan_policies`**: every policy now compares with
   `(SELECT current_setting('app.tenant_id')::uuid)`, which Postgres evaluates once per statement as an InitPlan
   and still uses for index conditions. `rls-bench-initplan.md`: catalog list +42.7% → −1.6%, category page
   +34.6% → +5.5%, admin orders +25.7% → +5.9%. Tenant-isolation tests still pass (missing context still fails).
2. The same plans exposed a **multi-tenant scaling bug independent of RLS**: `exists (variants ⨝ inventory)` in the
   select list of the storefront list and candidate queries was planned as a hashed subplan over the whole
   `inventory_items` table — 28.5 ms for 24 rows with 40 tenants. It is now a correlated
   `coalesce((select bool_or(…) … where v.product_id = p.id), false)`: **28.5 ms → 0.97 ms** (`EXPLAIN ANALYZE`
   on the 40-tenant copy); catalog list endpoint p50 ≈ 6.7 ms → ≈ 5 ms between runs.
3. `rls-bench.md` (final, both fixes, load 3.2–3.4): see the table below.

| Level | What | No RLS → RLS p50 | Overhead p50 (95% CI) |
|---|---|---|---|
| SQL, statement only | point lookups (category, product, variants, order detail, stock update) | 0.07–0.17 ms | +2.4% … +8.8% |
| SQL, statement only | list/search/suggest/admin list | 0.8–2.9 ms | −22.4% … +4.7% (RLS plans are often better: the tenant predicate reaches every subquery) |
| SQL, whole transaction | point lookups incl. the extra `set_config` round trip | e.g. 0.150 → 0.204 ms | +21.5% … +37.1% (≈ +0.05 ms absolute) |
| HTTP | catalog list / category page | 4.88 → 5.25 / 4.68 → 5.18 ms | +7.6% [+6.2, +9.7] / +10.8% [+8.2, +13.7] |
| HTTP | PDP, add to cart, admin orders, order detail, admin products | 1.4–7.3 ms | +2.7% … +8.0% (every CI excludes 0) |
| HTTP | search suggest | 3.43 → 3.17 ms | −7.7% [−9.6, −5.8] |

Conclusion: with InitPlan policies RLS costs **≈ 0.05 ms per transaction** (the `set_config` round trip) plus
**3–11% at the endpoint p50**; p95 overheads are in the same range (−7% … +8%). Absolute numbers differ between the
three runs because machine load differed; only the interleaved within-run comparisons are meaningful.

### 4. Fake payment webhook survives an API restart

The fake provider used an in-process `setTimeout`, so a restart inside `FAKE_PAYMENT_DELAY_MS` (2 s) left the order in
`pending_payment` forever. Now `confirmFake` inserts the signed-later webhook body into `fake_payment_webhooks`
(migration `0004`, tenant table with FORCE RLS, added to the isolation test) **in the same transaction** that moves
the payment to `processing`. `FakeWebhookDispatcher` wakes a timer after commit and also polls every
`FAKE_PAYMENT_POLL_MS` (1 s); both claim due rows with `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` and a
15-second lease, sign at send time (so the 5-minute signature tolerance never expires for old rows), retry with
backoff up to 6 attempts on network errors/5xx/429 and mark the row `delivered`/`failed`. Delivery is at-least-once;
the webhook handler's `payment_webhook_events` dedupe makes it exactly-once in effect. Test
`apps/api/test/integration/fake-payment-restart.test.ts` runs the API as a child process: confirm → `SIGKILL` after
16 ms → new process on the same port → **API back after 1.38 s, order `paid` after 2.16 s (delay 2.0 s)**, one webhook
row, one `paid` status change; a second case lets the webhook become due while the API is down; a third points the
dispatcher at a closed port and checks retries with `last_error`, then delivery. Smoke also checks the row.
