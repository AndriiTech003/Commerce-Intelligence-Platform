# 06 · Движок персонализации

Главная идея: **LLM генерирует варианты, но решает не LLM.** Решение принимает прозрачный алгоритм, который учится на поведении и объясняет каждое решение реальными признаками. LLM вызывается офлайн, никогда не в hot path.

```text
события ──► Профиль ──► Сегменты ──┬──► Кандидаты товаров ──► Ранжирование ──┐
                                   │                                          ├──► Decision + Explanation
          LLM (офлайн) ──► Креативы ──► Review ──► Bandit (Thompson) ─────────┘
                                                        ▲
                               impression / click / conversion
```

---

## 1. Профиль покупателя

Ключ: `profile:{tenant}:{profileId}`, где `profileId` = `customer_id`, если известен, иначе `anonymous_id`.

### Признаки

| Признак | Как считается |
|---|---|
| `aff.cat.{path}` | Аффинити к категории (для каждого уровня пути: `running`, `running.shoes`) |
| `aff.brand.{brand}` | Аффинити к бренду |
| `aff.tone.{tone}` | Сколько раз кликал по креативам каждого тона |
| `price.ewma_cents` | EWMA цены просмотренных/купленных товаров (α = 0.2) |
| `price.band` | `low / mid / high` — положение `ewma` относительно квантилей цен в топ-категории (квантили считаются раз в час из ClickHouse) |
| `intent` | 0..1, намерение купить сейчас (см. ниже) |
| `sessions_30d`, `last_seen_at` | |
| `orders_count`, `ltv_cents`, `last_order_at` | Из `order.placed` / `order.refunded` |
| `used_discount` | Покупал ли со скидкой |
| `recent_products` | Последние 20 product_id (для похожих товаров и исключения купленного) |
| `purchased_products` | Купленные product_id (исключаются из рекомендаций на 30 дней) |

### Аффинити с экспоненциальным затуханием

Вес события: `view 1`, `search match 1.5`, `ad_click 2`, `add_to_cart 3`, `purchase 5`, `remove_from_cart −1`.

```text
score_new = score_old · 2^(−Δt / half_life) + weight        half_life = 7 дней
```

В хэше храним `score` и `ts` последнего обновления. Затухание применяется лениво при чтении и при записи — фоновый пересчёт не нужен.

Это **коммутативно** с точностью до времени события, поэтому порядок обработки сообщений не важен. Нужно только передавать `occurred_at` события, а не время обработки (объяснить в ADR — именно это позволяет масштабировать consumers без партиционирования по пользователю).

Обновление — атомарный Lua-скрипт в Redis (read-decay-add-write в одной операции), по батчу событий одного профиля.

### Intent score

За последние 30 минут сессии:
```text
x = 0.15·views + 0.6·cart_adds + 1.2·checkout_started + 0.4·repeat_views_same_product + 0.3·search
intent = 1 − e^(−x)           (0..1, насыщается)
```
Коэффициенты подобраны вручную и описаны в README **как эвристика** («на реальных данных заменил бы на логистическую регрессию, обученную на исторических сессиях → конверсия»). Честность про ограничения — это плюс.

### Склейка профилей (identity stitching)

`customer.identified {customer_id, anonymous_id}` → merge анонимного профиля в профиль покупателя (сумма аффинити с учётом затухания, объединение списков) → анонимный ключ помечается как ссылка на customer (`profile:{t}:{anon}` → `{alias: customerId}`, TTL 30d).

Снапшот профиля в Postgres (`customer_profiles`) раз в 10 минут для изменившихся профилей (set `profile:dirty:{tenant}`) — для админки, превью сегментов и восстановления после потери Redis.

## 2. Сегменты

Правила — JSON, вычисляются в памяти (без обращения к БД):

```json
{
  "all": [
    { "feature": "aff.cat.running", "op": "gte", "value": 5 },
    { "feature": "price.band", "op": "in", "value": ["mid", "high"] },
    { "any": [
      { "feature": "intent", "op": "gte", "value": 0.6 },
      { "feature": "orders_count", "op": "gte", "value": 1 }
    ]}
  ]
}
```

Операторы: `eq, neq, gt, gte, lt, lte, in, not_in, exists, within_days`. Валидация zod, компиляция в функцию-предикат при загрузке (кэш по версии сегментов).

Системные сегменты (создаются для каждого тенанта):

| key | Правило |
|---|---|
| `new_visitor` | `sessions_30d <= 1 && orders_count == 0` |
| `high_intent` | `intent >= 0.7` |
| `returning_customer` | `orders_count >= 1` |
| `price_sensitive` | `price.band == low || used_discount` |
| `lapsed` | `orders_count >= 1 && last_order_at` старше 60 дней |
| `vip` | `ltv_cents` ≥ 90-й перцентиль тенанта (пересчёт раз в день) |

**Основной сегмент для bandit'а.** Профиль может попадать в несколько сегментов, а bandit'у нужно одно непересекающееся разбиение. Поэтому берётся сегмент с наименьшим `priority` среди `target_segments` кампании; если ни один не подходит — `_default`. Это важная деталь, про неё стоит написать ADR.

## 3. Рекомендации товаров

### Генерация кандидатов (≈ 200 штук)

| Стратегия | Источник | Где используется |
|---|---|---|
| `affinity_popular` | Топ-3 категории профиля → `reco:popular:{t}:{cat}` (Redis, обновляется раз в 10 мин из ClickHouse) | for_you, кампании |
| `vector_profile` | Средневзвешенный embedding последних 10 товаров профиля (веса = вес события × затухание) → pgvector kNN, `where tenant_id = … and status = 'active' and in_stock` | for_you |
| `vector_item` | Embedding текущего товара → kNN | similar (PDP) |
| `co_occurrence` | `reco:cooc:{t}:{product}` — совместные просмотры в сессии (вес 1) и покупки в заказе (вес 5), затухание | bought_together, cart_upsell |
| `campaign_selector` | Товары из `product_selector` кампании | Блоки кампаний |
| `global_popular` | Fallback для холодного старта | Везде |

### Ранжирование (прозрачная линейная модель)

```text
score = 0.35·similarity         (cos к вектору профиля/товара, 0..1)
      + 0.25·affinity_norm      (аффинити категории товара / max аффинити профиля)
      + 0.15·popularity_norm    (log(1+views_7d) / log(1+max))
      + 0.15·price_fit          (1 − |log(price / price.ewma)| / log(3), обрезано в 0..1)
      + 0.10·freshness          (новые поступления)
Фильтры: нет в наличии, куплен за 30 дней, текущий товар
Разнообразие: максимум 2 товара одного бренда в топ-N; MMR с λ = 0.7 по embedding
```

Для каждого товара сохраняются **вклады признаков** (`contributions`) — из них строится объяснение.

Кэш результатов: `reco:res:{t}:{profile}:{type}` на 5 минут; инвалидация при значимом изменении профиля (например, add_to_cart).

### Embeddings товаров

- Текст: `title | brand | category path | ключевые атрибуты | первые 500 символов описания`.
- Модель задаётся конфигом (`EMBEDDINGS_PROVIDER=openai|voyage|local`); для локальной разработки — модель через HTTP-контейнер (например, `text-embeddings-inference`), чтобы не платить за API.
- `embedding_version` в таблице → команда `pnpm reembed --version=…` пересчитывает всё в фоне.
- Вызов — в `domain-worker` по событию `product.upserted`, батчами по 64.

## 4. Креативы через LLM

### Генерация

`POST /campaigns/:id/creatives/generate {segments: ['high_intent','price_sensitive'], tones: ['performance','value'], count: 3}`

Вход в промпт (**только агрегаты, без PII**):
- Описание магазина и brand voice (из настроек тенанта).
- Товары кампании: топ-10 по популярности — название, ключевые атрибуты, диапазон цен.
- Описание сегмента: человекочитаемое описание правил + агрегированные признаки (например: «средняя цена просмотров $95, топ-категории running.shoes, 62% уже покупали»).
- Тон и ограничения: длины, запрещённые утверждения, реальные активные скидки (если есть).

Выход — **структурированный JSON** (tool use / structured output): `{ variants: [{ headline, body, cta, tone, rationale }] }`, валидируется zod. Невалидно → один ретрай с текстом ошибки валидации, дальше ошибка.

### Guardrails (детерминированные, после генерации)

| Проверка | Действие |
|---|---|
| Длина headline ≤ 60, body ≤ 160, cta ≤ 24 | reject |
| Упоминание цены или процента → должно совпадать с реальной ценой или активной скидкой | флаг `unverified_claim` → не может быть approved без правки |
| «free shipping», «guaranteed», «#1», «best in the world» и т.п. (список в настройках тенанта) | флаг `banned_claim` |
| Профанити / токсичность (словарь + опционально moderation API) | reject |
| Почти дубль уже существующего креатива (cos > 0.92 по embedding) | флаг `near_duplicate` |
| Язык не совпадает с языком магазина | флаг |

Описания товаров пишет мерчант, это **недоверенные данные**: в промпте они в отдельном блоке с разделителями и инструкцией не выполнять из них команды. Тест с описанием товара, содержащим «ignore previous instructions…», проверяет, что guardrails ловят результат.

### Операционные детали

- Промпты лежат в `apps/api/src/modules/campaigns/prompts/creative.v{N}.md` и версионируются. В креативе сохраняется `promptVersion`, `model`, `inputHash`, токены, латентность, стоимость.
- Кэш по `inputHash` — повторная генерация с тем же входом не тратит деньги (для демо важно).
- Лимиты: не более N генераций на тенант в день (демо-защита от расходов).
- Интерфейс `LlmClient` с реализациями: реальный провайдер (модель в конфиге) и **`FakeLlmClient`** (детерминированные шаблоны) для тестов, CI и офлайн-демо.
- **Eval-скрипт** `pnpm eval:creatives`: 20 фикстур (кампания × сегмент × тон) → генерация → доля прошедших guardrails, средняя длина, доля дублей. Результат — в README. Это отличает инженерный подход от «подключил ChatGPT».

### Review

Статусы: `draft → approved | rejected`, `approved → active ⇄ paused`. Одобрять может только пользователь с `marketing:approve`. Есть интерфейс «ревью-очереди» с подсветкой guardrail-флагов. В bandit попадают только `active`.

## 5. Выбор креатива: Thompson sampling

Для каждой пары `(campaign, segment)` и каждого активного креатива (arm) хранится:
```text
n = показы, s = успехи (клики или конверсии — по goal кампании)
Beta(α = 1 + s, β = 1 + n − s)
```

**Решение:** для каждого arm сэмплируем `θ ~ Beta(α, β)` и выбираем argmax. Сэмплер Beta пишется самостоятельно через два Gamma-сэмпла (Marsaglia–Tsang), с **seeded PRNG** для детерминированных тестов. Тест проверяет среднее и дисперсию на 100k сэмплов.

**Обновление:** `ad_impression → HINCRBY n +1`, `ad_clicked → HINCRBY s +1` (Lua, атомарно). Для goal = `conversion`: `order.placed` с `attribution.decisionId` (last-click в окне 24 ч) → `s +1`.

Дедупликация показов: одинаковый `decision_id` засчитывается один раз (`SET NX`).

**Детали, о которых стоит написать в README:**
- **Задержанная обратная связь.** Показ засчитывается сразу, клик позже, поэтому оценки ненадолго занижены. Для кликов это секунды и не критично, для конверсий (до 24 ч) — известное ограничение.
- **Нестационарность.** Опциональный discount factor γ (например, 0.999 на каждое обновление) или скользящее окно, чтобы bandit адаптировался к смене вкусов. В демо это показывается переключателем в симуляторе: «поменять предпочтения персоны».
- **Минимальная разведка.** Первые 50 показов на arm — равномерно (warm-up).
- **Новый креатив** начинает с приора Beta(1,1) и быстро получает трафик за счёт неопределённости.
- Снапшот состояния в Postgres каждые 5 минут (`bandit_snapshots`) нужен для восстановления и для графиков истории.

### Статистика для экрана эксперимента

- CTR/CVR с **интервалом Уилсона 95%**.
- **P(best)** — доля побед arm в 10 000 совместных сэмплах.
- Доля трафика по arm во времени (из `decisions` в ClickHouse, по часам).
- В режиме симулятора дополнительно: **кумулятивное сожаление (regret)** относительно оракула, который знает истинные CTR, и сравнение с **равномерным A/B** (симулятор может вести параллельную «теневую» политику). График «Thompson потерял 180 кликов, равномерный A/B — 1 240» — сильный момент демо.

## 6. Объяснение («Why this ad?»)

Каждое решение сохраняет explanation. Человекочитаемый текст собирается **шаблоном**, а не LLM, чтобы в объяснении не было ничего выдуманного.

```json
{
  "decisionId": "0192…",
  "segment": {
    "key": "high_intent_runner",
    "matchedRules": ["aff.cat.running = 8.2 ≥ 5", "price.band = mid", "intent = 0.81 ≥ 0.6"]
  },
  "profileSignals": [
    "Viewed 4 running products in the last 24h",
    "Purchased \"Pegasus 41\" 12 days ago",
    "Typical price range $80–150"
  ],
  "creative": {
    "chosen": "c_7f…",
    "headline": "Built for your next 10K",
    "policy": "thompson_sampling",
    "arms": [
      { "id": "c_7f…", "tone": "performance", "impressions": 1840, "ctr": 0.052, "sampled": 0.057, "pBest": 0.81 },
      { "id": "c_a3…", "tone": "lifestyle",   "impressions":  610, "ctr": 0.031, "sampled": 0.029, "pBest": 0.12 },
      { "id": "c_19…", "tone": "value",       "impressions":  402, "ctr": 0.027, "sampled": 0.034, "pBest": 0.07 }
    ]
  },
  "products": [
    { "id": "p_1", "score": 0.78, "contributions": { "similarity": 0.29, "affinity": 0.25, "popularity": 0.11, "priceFit": 0.13 } }
  ]
}
```

UI: иконка «ⓘ Why this?» на витрине (включается в demo-режиме) и страница решения в админке.

## 7. Симулятор трафика (`apps/simulator`)

Без симулятора персонализация на демо выглядит мёртвой. С ним видно, как система учится.

### Персоны (`simulator/personas.yaml`)

```yaml
personas:
  - key: marathon_runner
    share: 0.30
    categories: { running.shoes: 0.5, running.apparel: 0.3, running.watches: 0.2 }
    price: { mean: 120, sd: 30 }
    session: { pages_mean: 7, add_to_cart_p: 0.18, checkout_p: 0.55, purchase_p: 0.8 }
    return_rate: 0.4            # вероятность вернуться (тот же anonymous_id)
    register_p: 0.3             # вероятность зарегистрироваться при покупке
    base_ctr: 0.03
    tone_multipliers: { performance: 1.8, lifestyle: 0.8, value: 0.9, premium: 1.1 }   # скрытая «истина»
  - key: weekend_hiker       # outdoor, mid price, lifestyle ↑
  - key: bargain_hunter      # low price, value ↑↑, отзывчив к скидкам
  - key: window_shopper      # много просмотров, почти не покупает
  - key: gift_buyer          # случайные категории, premium ↑
```

### Модель поведения (на каждую сессию)

```text
land (home | category | product из «рекламы»)
 → запрос decision для placement → показ (ad_impression)
 → клик с p = base_ctr · tone_multiplier[creative.tone] · relevance(products, persona)
 → просмотр товаров, выбранных по распределению категорий персоны и близости цены
 → add_to_cart / checkout / оплата с вероятностями персоны (через настоящие API)
 → конец сессии; с вероятностью return_rate визит повторится через N минут
```

Симулятор ходит **через реальные публичные API** (storefront + collector + fake payment), поэтому он одновременно работает как E2E-нагрузка.

### Режимы

| Режим | Назначение |
|---|---|
| `live` | Реальное время, 1–50 сессий/сек, управление из админки (старт/стоп, rate, доли персон) |
| `backfill --days=90` | Генерирует историю за 90 дней с прошлыми `occurred_at` напрямую в MQ (минуя HTTP), чтобы на графиках, в когортах и воронке были данные |
| `shift` | На лету меняет `tone_multipliers` персоны, чтобы показать адаптацию bandit'а (с discount factor) |
| `load` | Максимальная интенсивность для нагрузочного теста всего пайплайна |

### Экран «Ground truth vs learned» (demo only)

Таблица: персона → истинный лучший тон | сегмент, в который она в основном попадает → тон, который выбрал bandit (P(best)). На демо видно, что система **сама нашла** скрытые предпочтения. Это главный «вау»-момент проекта.

## 8. Метрики качества персонализации (в README)

- CTR персонализированного блока vs контрольная группа: 10% трафика получает `global_popular` и случайный креатив (holdout). Считается в ClickHouse.
- Latency decision API: p50/p95/p99.
- Доля решений с холодным стартом (пустой профиль).
- Покрытие каталога рекомендациями (сколько разных товаров хоть раз рекомендовано).

Все цифры с пометкой «on simulated traffic» — честно.
